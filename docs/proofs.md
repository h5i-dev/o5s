# Proofs and the trust boundary

`h5i app extract .` extracts `crates/kernel/src/patch.rs::merge` through Charon and Aeneas into `proofs/generated/O5sKernel.lean`. The platform's `h5i_app_core::Kernel` adapter calls that same Rust function. The proof relates the extracted admission function to its specification.

`Patch.lean` proves:

| Theorem | Statement |
|---|---|
| `merge_spec` | Success/refusal exactly follow review, check and dependency guards; successful output is set insertion. |
| `merge_authorized` | A successful extracted execution has approval, passing checks and all dependencies present. |
| `no_lost_patch` | Every earlier patch remains after successful admission. |
| `dependency_closed` | An existing dependency-closed channel stays closed when the registry-supplied dependency list is admitted. |
| `successful_orders_converge` | Two patches successfully admitted in either order give equal set membership, using actual extracted executions. |
| `insert_idempotent` | Repeated insertion has the same membership. |
| `delivery_converges` | Arbitrarily long finite deliveries with equal patch membership converge in the set specification. |

Set equality means equal membership, not equal vector order or equal Git commit hashes. Dependent patches must be delivered in an admissible order; a missing dependency is refused. The capacity precondition excludes a vector length beyond `Usize.max`. Allocation failure, compiler correctness and extraction correctness are outside the theorem.

The registry assigns local numeric handles to full SHA-256 records; these handles are not hashes and are not shared across independent replicas. Content, author, intent and dependency hashes enter the immutable identity. Reviews attach to immutable records. Approvals/check facts and dependencies are supplied by the authenticated server, never by the caller of the merge command. The proof assumes these inputs correctly describe that record. Cryptographic identity, reviewer independence and tenant authorization are not themselves proved in Lean.

## Graph projection

`crates/kernel/src/graph.rs::reachable` delegates to h5i-app's graph primitive and is also extracted. `Projection.lean` proves `live_reachability`: an exact live-boundary summary preserves reachability between live endpoints, including cyclic graphs. `incremental_summary` proves that replacing only touched-source edges preserves the summary invariant **provided** the old and newly computed summaries are correct and dead-interior reachability outside the touched components is unchanged. `extracted_projection` relates two successful executions of the actual extracted Rust search, under that summary invariant, live endpoints, a singleton start and vector-capacity bounds.

`Constructor.lean` proves `boundary_spec` for the actual extracted Rust constructor: its output contains precisely live endpoints reached by nonempty dead-interior walks. The proof covers the edge filters, initial successor list, search and live filter, under a vector-capacity bound. `summary_rows_spec` proves the outer Rust loop produces the correct row for every live vertex, in order.

`Components.lean` proves that weak-component isolation and equality of edges/liveness outside a component imply the previously assumed stability of dead-interior walks. Its batch theorem permits edge additions that join old components and liveness changes (deletion/restoration) seeded into those components. The reference Rust `weak_component` constructor is extracted and proved to return exactly reachability in the original edges plus their reversals. `extracted_batch_incremental` uses an actual successful execution of this constructor to obtain the touched set; old and fresh summary correctness remain explicit assumptions.

`Indexed.lean` proves `reachable_spec` for the actual extracted dense-adjacency Rust search: returned membership is precisely adjacency reachability from the seeds, the queue has no duplicates, and the reusable visited vector is returned entirely false with its length preserved. Its loop proof establishes bounded indexing, termination and integer-capacity safety. Inputs must have bounded neighbor/seed indices, an all-false vector of the same length as the adjacency rows, and fewer than `Usize.max` rows. The native weak-component finder calls this proved search on persistent bidirectional adjacency rows; it clears only reached entries instead of allocating or scanning all vertex marks per update.

`Boundary.lean` proves the actual extracted indexed boundary constructor returns exactly live endpoints reached by nonempty dead-interior walks, provided adjacency rows represent precisely original edges from dead sources and the seeds represent direct successors. It proves the constant-time liveness filter and its composition with the reusable-mark search, preserving queue uniqueness and clean marks. The native summary constructor uses these same search/filter functions with persistent original/dead adjacency rows.

The external-ID/dense-index adapter and incremental maintenance of those rows in `crates/platform/src/projection.rs` are **not extracted or proved**. Exhaustive tests check every directed three-vertex graph and liveness assignment against the extracted Rust primitive and the universally proved boundary constructor; the indexed weak-component finder is checked against the proved reference on every three-vertex graph and seed subset (4,096 cases); additional tests cover edge insertion through deleted vertices, restoration, component isolation and a 10,000-vertex dead chain. The proof defines the invariant the constructor must satisfy; these tests supply implementation evidence, not a universal constructor proof. This graph module is separate from whole-file materialization. It does not prove file order, conflict rendering, byte-range editing or the completeness of Pijul's algorithm.

## Runtime scope

The file view uses causal multi-value registers: an edit supersedes ancestor edits on its path, concurrent values are retained, and equal concurrent values collapse in the displayed file while provenance stays in the registry. File/directory collisions and delete-versus-modify conflicts are explicit. Integration order independence, conflict preservation and resolution behavior are integration-tested. The materializer has not been extracted or proved; the set theorem must not be advertised as a proof of all merge behavior.

`h5i app check` scans hand-written proof modules and gates every theorem against only `propext`, `Classical.choice` and `Quot.sound`. The manifest additionally requires key admission theorems by name. Declared mutation tests reverse the approval, check and dependency guards in the actual Rust source; each must compile/extract and then fail the Lean proof. An invalid edit or compilation failure is not a caught semantic mutant.

The native store serializes transactions under a process-wide mutex, uses a process-lifetime file lock, writes a candidate snapshot and atomically replaces the state file. Tests cover concurrent API requests, rejected admission, restart and competing process locks.

Pinned Lean/Aeneas/h5i versions are recorded in `proofs/lean-toolchain`, `lakefile.lean` and `lake-manifest.json`. Generated Lean files are committed and regenerated, not manually edited. If interrupted builds exhaust disk and leave a corrupt `.olean`, remove the affected generated build artifact and rebuild; do not change the theorem to bypass the gate.

## Immutable-base line edits

`interval::conflict`, `interval::splice`, `interval::append_range`, `interval::render_chunks`, `interval::valid_chunks` and `interval::checked_render` are extracted Rust. The native line engine calls conflict detection and the extracted multi-range renderer. `Interval.lean` proves exact conflict detection, symmetry, strict-gap safety, the append-slice equation and the byte-splice equation `take(start) ++ replacement ++ drop(end)`. The splice theorem requires ordered, bounded byte offsets and sufficient vector capacity. `Splice.lean` proves independent byte edits commute, including four successful executions of the actual Rust splice primitive and the translated coordinates after replacement. Native code checks ranges and converts line offsets to UTF-8 byte boundaries. `Rendering.lean` proves the complete Rust multi-range loop returns the list specification for sorted, bounded byte intervals and sufficient capacity, including preservation of every untouched slice and the final suffix. The boundary-position scan is extracted and proved as described below; native range conversion, the neighbor index and combining versions remain tested trust-boundary code; these byte-level proofs are not a theorem about the complete text merge engine.

Each line proposal names an immutable base patch and zero-based half-open ranges. The server adds its base dependencies and rejects obsolete or conflicted causal bases. Disjoint concurrent ranges on the same base combine; overlapping distinct replacements, insertion/delete boundary ambiguity, and distinct bases remain conflicts. A newer base may itself be a line proposal's preview. This is a stable-coordinate merge model, not an implementation of Pijul's byte-interval graph algorithm.

`Checked.lean` closes the byte renderer's input-validation boundary. The actual Rust validator accepts exactly the recursive `Good` predicate: each range starts at or after the prior end, has ordered endpoints within the original bytes, and its replacement fits the remaining conservative capacity budget. The proof establishes sorted bounded intervals and `original length + sum of replacement lengths ≤ Usize.max` from acceptance. `checked_render_spec` has no coordinate or capacity preconditions: rejection returns `None`, and acceptance returns precisely the multi-range list specification. This covers integer overflow and indexing safety in the extracted semantics, not allocation failure, UTF-8 decoding or the native range adapter. The native adapter uses this checked Rust entry point directly.

`Coordinates.lean` proves the actual Rust LF-delimited boundary scan, which the native line renderer calls directly. Its output equals the byte-by-byte specification, positions are bounded by input length and strictly increase, and loop/index/integer/vector-capacity safety follows under `input length < Usize.max`. A trailing LF does not add an extra empty line; a nonempty input ends at its byte length and an empty input has the single zero boundary. The proof is about byte positions, not Rust UTF-8 decoding. Converting proposal coordinates to `usize`, building replacement tuples and decoding the rendered bytes remain native trust-boundary code. Differential tests exercise 19,531 UTF-8/CRLF/LF strings against Rust's line slicing and check every position is a character boundary.
