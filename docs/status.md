# Implementation status

This repository is a local MVP, not the complete distributed Git platform described in the project brief. Verification of individual kernels does not establish correctness of the entire application.

| Area | Implemented | Remaining boundary |
|---|---|---|
| Patch collaboration | Every registry decision by the extracted `o5s_registry::transition`: immutable identities, dependency-closed channels, independent approvals/check reports, atomic batch admission, tenant isolation. `o5s ci` executes checks on the immutable snapshot each proposal defines (`GET /api/snapshot`) and reports them | Authenticated identity and SHA-256 identities are supplied by native code. Checks run where `o5s ci` runs; there is no hosted runner or sandbox |
| Text merge | Whole-file/line conflict alternatives and block-graph insertion, deletion tags, restoration, reviewed order and order retraction (cycle recovery); resolutions are proposals. Graph documents are validated, committed and materialized by the extracted `document` kernel; line ranges are validated, merged and rendered by the extracted `lines` kernel; causal heads by `causality` | Semantic conflict resolution is manual. A move keeps a graph document's identity; other renames are a removal and an addition |
| Graph acceleration | Dense indexed traversal, reusable marks, affected-component live-boundary summaries, extracted reference/refinement proofs | Graph documents call the extracted boundary traversal; the component-local projection cache remains separate, and native graph adapters are unproved |
| Storage | Local checksummed write-ahead log; PostgreSQL with one READ COMMITTED transaction per command under its repository's advisory lock (`o5s_pgwire`), narrow per-command loads, idempotency keys, retries and multi-replica reads; backup/verify/import tools; metrics and readiness | Narrow loads are proved sound (`narrow_load`), and so is the loader's model, branch by branch, and grouped transactions (`pg_served`, `group_served` in `crates/registry/proofs/`), assuming PostgreSQL's `WHERE` and `ORDER BY` behave as specified; no cross-region replication; a hot repository is limited by per-transaction roundtrips |
| Git/worktrees | User/agent CLI with native Git worktrees, proposals, review, checks, conflict resolution and safe snapshot fetch; regular, executable, binary, symlink and submodule entries; local bare Git export | No Git smart-HTTP server |
| Cloudflare | Rust Worker (`crates/worker`) running the same kernel and `o5s_pgwire` service over Hyperdrive, built with `worker-build` and exercised end to end in local `workerd`; deployed at `o5s.koukyosyumei.workers.dev` (PlanetScale Postgres via Hyperdrive) and checked end to end; Git projections and agent workspaces in Cloudflare Artifacts | Git export pushes to Artifacts from the Worker (`crates/gitpush`). Agents get clone access through `GET /api/artifacts` and their own workspace repositories through `/api/worktree`; proposals are read from pushed branches with `readTree`/`readBlob`. The workspace flow is unit-tested against Git-built trees and not yet run on the live deployment |
| Formal verification | Registry: refinement of a pure model, the invariant on every reachable state, history, admission gate, isolation, narrow loads, and that the PostgreSQL loader serves narrow loads. Kernels: admission, reachability and boundaries, intervals, checked rendering, frontiers, tags; the extracted `lines` and `causality` functions against their models; and the graph-document model (validation reads only the causal past, admissions commute, any topological delivery converges to the same view, which exists and is unique). All gated without `sorry` | The extracted `document` functions are proved against the document model (gated): the extracted `validate` refuses exactly when the model does, with the model's error, a validated patch commits to a document that again encodes the history (`DocRefine.lean`), and the decoded result of the extracted `materialize` is the specified view, so two replicas with the same patches in any orders materialize the same view (`DocMatRefine.lean`). The size assumptions are explicit (`Room`, `CommitRoom`, `RoomM`). Native authentication, hashing, Git behaviour and the Cloudflare runtime are trusted |
| Scale | Rust HTTP driver: 1,000 authors at 64 in flight, local log 800–2,600 proposals/s, PostgreSQL 430–3,700/s with group commit; open-loop sweep to saturation (about 500/s on one repository); measured Git baseline | No 10,000-client or multi-host measurement |

The extraction and proof gate cover the o5s kernels. The axiom gate checks actual extracted Rust refinements as well as supporting mathematical lemmas; a theorem count is not a count of end-to-end product guarantees.

The block-graph path is connected to persisted proposals, admitted channel views and Git exports. Ordinary Git edits to existing graph documents produce graph operations with their original snapshot dependencies, both through `o5s propose` and from agent workspaces (native worktrees and Artifacts branches), whose proposals depend on the snapshot's causal heads. Initial graph creation from ordinary Git is implemented. Legacy document migration, empty-file creation, graph path deletion and component-local updates remain unfinished. Native transaction/persistence behavior and distributed execution also need explicit specifications before end-to-end verification can be claimed. Research-derived compression or incremental ordering should be accepted only with measured benefit and a refinement argument for this model.

The [production roadmap](roadmap.md) defines the missing semantics, implementations, proofs and operational acceptance tests.
